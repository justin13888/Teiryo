# Architecture

## Process model

- Two processes: `teiryod` (daemon) and `teiryo` (TUI client). Providers are compiled in — no plugin or dylib loading.
- **Startup**: `teiryo` spawns `teiryod` on first connect if the socket is unreachable — tmux's client/server pattern. The child calls `setsid()` before exec, so it leads a session of its own with no controlling terminal, and starts in `/`, so it never pins the directory (or the volume) the TUI was launched from. It starts from a cleared environment and keeps only `HOME`, `PATH`, `USER`, `TMPDIR`, `LANG`, `TEIRYOD_LOG`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_RUNTIME_DIR` and every `TEIRYO_*` variable: the daemon outlives the TUI that spawned it and serves every later one, from any shell, so it must not carry the first shell's mise `[env]` values, proxy and certificate settings, or `cargo run` variables. The `XDG_*` directories stay because the socket, config, database and log paths resolve from them, and a daemon that resolved them differently from the TUI would bind or log where the TUI never looks. Its stdout/stderr go to the log file, and it is reaped in the background so it never lingers as a zombie. No manual double-fork.
- **Single instance**: an exclusive, non-blocking `flock` on `teiryo.lock` beside the socket, taken before anything touches the socket and held for the process lifetime. Losing it means another daemon is starting or running → exit 0. The kernel releases it however the holder dies, `kill -9` included, so it can never go stale. The lock file is never unlinked: removing it while held would let a third process lock a fresh inode alongside the holder.
- **Stale socket**: only the lock holder handles one. On `EADDRINUSE` it connects as a client first: `ECONNREFUSED` means the socket is stale from a crash → unlink and rebind; an answer means a daemon from a build without the lock still serves there → exit 0 and leave it alone.
- **Signals**: SIGINT, SIGTERM and SIGHUP handlers are installed before the bind, so a signal at any point after it is a clean shutdown rather than a default-action death that leaves the socket behind.
- **Shutdown**: a signal or the `Shutdown` request → flush DB, unlink socket. The unlink is a drop guard that removes the socket only while its `(dev, ino)` still match what this process bound, so an orphan cannot delete a newer daemon's socket, and the early error paths (opening the database, registering the listener) unlink through the same guard. The TUI quitting never kills the daemon; daemon shutdown is only via the explicit `Shutdown` request or a signal. A shutdown does not stick while another TUI is open: the TUI that sent `Shutdown` quits, but every other one sees its connection drop and respawns the daemon on its next reconnect attempt.
- **Install and uninstall** (`scripts/install.sh`, which `mise run install` runs as `--from-source` and which installs a release archive otherwise, and `mise run uninstall`): both refuse while a `teiryo` TUI runs, because it would respawn the daemon they stop, from whichever build it came from. Install asks the installed `teiryod` for its socket and log paths, stops every live `teiryod` of the user, then takes the instance lock itself and removes the socket only while holding it, so a live daemon's socket is never deleted; a lock it cannot take means a daemon survived, and install fails. It starts the new daemon in a session of its own (`setsid`, or perl's `POSIX::setsid` on macOS, which has no `setsid(1)`) with its output appended to the log, and succeeds only once the socket exists and a live `teiryod` is the installed binary, by `/proc/PID/exe` on Linux or `ps -o comm=` on macOS.
- **Reconnect**: a TUI that loses the daemon reconnects in a background task, so it keeps drawing and handling keys meanwhile. Attempts back off from 1 s, doubling to a 30 s cap, and each may spawn the daemon once. The handshake is bounded at 15 s, so a daemon that accepts but never answers cannot hang the client. The bound sits above a fresh daemon's worst-case work before it accepts (opening the database, then account discovery, which on macOS may wait up to 5 s on a Keychain read), so a slow first launch waits rather than fails. A daemon that rejects the client's protocol version ends reconnecting for that TUI: retrying would only respawn a daemon that exits against the stale one, so the header says to stop it instead.

## Crate layout

```
teiryo/                    # workspace root
  crates/
    teiryo-core/           # domain types, wire protocol, adapter traits, storage
    teiryo-providers/      # claude, openai, ... — implement teiryo-core traits, own their deps
    teiryod/               # daemon bin: scheduler, IPC server, wires providers + storage
    teiryo/                # TUI bin: ratatui + crossterm
```

**Dependency rules (invariant):**

- `teiryo` (TUI) depends only on `teiryo-core`. It must never gain provider internals, HTTP, DB, or scheduling code.
- Provider adapters live in `teiryo-providers`, not `teiryo-core`, so credential-store dependencies and per-provider trait impls stay out of the light, stable crate the TUI links against.
- The adapter registry is a `Vec<Box<dyn ProviderAdapter>>` built by hand in `teiryod`'s `main()` — the provider count is small; no registration framework.

## Scheduler & live updates

- One polling task per **(provider, account)** pair — a probe returns all of that account's windows in one call, so per-provider tasks would be too coarse and per-window tasks too fine. Tasks are spawned/aborted as `Authenticator::discover_accounts()` adds/removes accounts; handles live in `HashMap<(ProviderId, AccountId), TaskHandle>` in daemon state.
- Discovery runs for **every** compiled-in provider, including ones disabled in config: it is a local credential read, and skipping it would leave a disabled provider with no accounts and no task, so enabling it could not take effect without a daemon restart. `enabled` gates polling, in the task, not discovery.
- **A provider with no accounts keeps discovering.** When startup discovery fails or finds nothing, a re-discovery task re-runs it on the credential re-check's cadence (the configured cadence or 30 s, whichever is shorter, jittered) until it finds accounts, then starts each through the same path startup uses and exits. A login made after the daemon started is therefore polled within about one re-check, without a restart. Each attempt replaces or clears the provider's `discovery_error`, and a failure is logged only when its message changes. While the provider is disabled the task waits on the config instead, and re-enabling it re-discovers at once.
- Each task owns an `mpsc::UnboundedSender<PollTrigger>`. Every cycle it asks what to do next — poll now, sleep then poll, re-check a credential, or park — and each answer is a `select!` whose arms include `Some(t) = rx.recv() => t` alongside its own timer. A manual `PollNow` is therefore a message injected into whichever wait is currently running, tagged with the requesting client: it is never held back by a backoff or a pause, and needs no separate code path around either.
- Each task also owns a `watch::Receiver<Schedule>` (`{ enabled, interval }`), re-read every cycle. Cadence is therefore **not** captured by value at spawn: a config reload publishes to the channel and the running task picks it up, and a `changed()` arm re-arms the sleep so a shortened interval takes effect at once rather than after the old one finally elapses. A disabled provider's tasks **park** on that channel instead of ticking and discarding, and `PollNow` against a disabled provider is refused rather than queued into a parked task.
- **Live updates**: one global `tokio::sync::watch::Sender<Option<PollEvent>>`, published after every completed probe, and a second `watch::Sender<u64>` carrying the config generation. `AwaitUpdate { since, config_gen, timeout_ms }` waits on both and returns whichever is already newer, or whichever lands first. Two built-in channels, no pub/sub crate, no per-subscriber bookkeeping. A single global poll channel (not per-account) is deliberate: clients wake for accounts they aren't viewing, which is free to ignore.
- Poll jitter is recomputed each cycle, not fixed per task. The base cadence defaults to **180 s**: quota figures move slowly enough that a minute of extra resolution buys nothing actionable, while costing three times the requests against an endpoint that rate limits.
- **Rate-limit backoff** lives in the poll task, next to the jitter, because it is a property of the credential rather than of the config — it must not travel over the `Schedule` channel or a config reload would clear it. Each consecutive `RateLimited` outcome doubles the wait (capped at 1 h; a provider's own `Retry-After` wins over both the doubling and the cap), and any other outcome *that reached the provider* clears the strikes outright. The throttled interval is never shorter than the configured cadence. A manual `PollNow` is *not* held back — the user asked for that one, and a success through it clears a stale backoff. Tasks republish the throttled interval into `poll_intervals`, so a client's "next poll in" countdown reflects the backoff instead of hitting zero and sitting there.
- **A poll that never reached the provider cannot speak for it.** The task records how far each poll got, and a poll that died resolving the local credential sent no request: it neither adds a strike nor clears one. Anything else would let an expired token silently discard a backoff the provider had asked for, so a re-login hours later resumed at full cadence straight back into the rate limit.
- **An unusable credential pauses probing rather than repeating it.** While the local credential fails to resolve, the task stops polling and instead re-resolves that credential alone — no request, nothing written — at the configured cadence or 30 s, whichever is shorter, resuming with a full poll the moment it succeeds. Claude access tokens last ~12 h and only `claude` renews them, so without this an overnight expiry spent hours issuing probes that could not authenticate. Recovery triggers on the `Err` → `Ok` edge, never on `Ok` itself: a token the *provider* rejects still resolves locally, so levelling on `Ok` would poll, take its 401, and poll again on every re-check. A provider rejection is therefore left to the rate-limit path above, unchanged. A paused account republishes a cadence of `0` — nothing is scheduled, so there is no countdown to offer — and a manual `PollNow` still goes straight through, since resolving the credential is part of the poll it performs. Precedence is what keeps a *disabled* provider out of this entirely: it parks before its credential is ever considered. Pausing outranks the rate-limit wait, so an account that was already being throttled when its token expired resumes on the credential rather than on the remaining backoff, and may spend one request early; the pause has itself imposed a gap of at least the re-check interval, and a request that is still limited simply doubles the wait again. Both edges are reported when that happens, so the backoff that follows a resumption is never unexplained.
- **The daemon never refreshes or writes a credential.** It reads whatever the provider's own CLI left on disk and reports what it finds. Refreshing would mean holding a refresh token the vendor rotates on use and writing the rotated pair back into the file that CLI owns, so a bug or a write race there logs the user out of the tool teiryo is merely observing. The pause above is the deliberate alternative: notice quickly, cost nothing, and let the user's own login flow be the only thing that mints a token. Revisiting this is a decision about that risk, not about the scheduler.
- **Stalls are logged on their edges**, once entering and once leaving, with the outage's duration on the way out. Logging the level instead is what turned a single three-hour stall into 180 identical warnings.

## Async runtime & HTTP

- `tokio` with the `current_thread` flavor. Tasks are numerous but I/O-bound and idle almost always.
- `reqwest` with `rustls-tls` (no system OpenSSL).
- One persistent `reqwest::Client` per **account** — separate accounts must not share a connection pool or cookie jar. Clients are reused across probes for connection fidelity (matching the real client's connection-reuse behavior).
- Header order/UA and connection-reuse fidelity to each provider's real client is a v1 goal. Exact TLS-stack fingerprint (JA3) match is an accepted gap — not solved via spoofing.

## Config & paths

- XDG resolution via the `directories` crate.
- `$XDG_CONFIG_HOME/teiryo/config.toml` — per-provider enable/disable, poll interval overrides, and (deferred) `[[account]]` entries for providers that cannot be auto-discovered.
- `teiryo/teiryo.db` and `teiryo/teiryo.log` in the platform's data directory: `$XDG_DATA_HOME` on Linux, `~/Library/Application Support` on macOS. `teiryod --print-log-path` prints the log's path, creating its directory.
- The socket, resolved by `teiryo_core::paths::socket_path()` — the one rule both binaries use, and what `teiryod --print-socket-path` prints:
  - macOS: `teiryo.sock` in the per-user temporary directory, `confstr(_CS_DARWIN_USER_TEMP_DIR)` (falling back to `$TMPDIR`), which the system creates mode 0700. It does not follow a changed `$TMPDIR`, so every process of the user agrees on it.
  - Elsewhere: `$XDG_RUNTIME_DIR/teiryo.sock` when the variable is absolute (a relative one is ignored, per the XDG spec).
  - Both fall back to `/tmp/teiryo-$UID.sock`, also when the candidate is longer than the 103 bytes `sun_path` can hold on macOS.
  - Socket file mode 0600; the lock is the same name with a `.lock` extension, also 0600, opened `O_NOFOLLOW`.
- **Debug builds are kept apart.** Under `cfg(debug_assertions)` (what `cargo run` and `mise run tui` build) the socket is `teiryo-dev.sock` (fallback `/tmp/teiryo-dev-$UID.sock`, lock `teiryo-dev.lock`) and the database and log live in `teiryo-dev/` instead of `teiryo/`. A daemon spawned from a checkout therefore serves only debug TUIs and writes only its own database, so it can neither capture installed TUIs nor fail their handshake with a bumped protocol, and an installed daemon and a debug one run side by side. `config.toml` stays shared: both read and write `teiryo/config.toml`. The names and the resolvers built on them live in `teiryo_core::paths` (`SOCKET_NAME`, `DATA_DIR_NAME`, `socket_path`, `data_dir`, `log_path`), which both binaries use, so the TUI sends a spawned daemon's output to the log that daemon writes; the release names above are unchanged.

### Hot reload

The daemon watches `config.toml` (`notify`, on the containing **directory** — editors replace config files by rename, which leaves a file watch pointing at a dead inode; a ~200 ms debounce coalesces the write burst one save produces) and re-reads it on every change.

**One apply path.** Startup, `SetConfig`, and the watcher all funnel through the same `Daemon::apply_config`, which republishes every account's `Schedule` and bumps the generation. There is one place where a setting becomes real, so the three cannot drift.

**The daemon is the only writer clients go through, but not the only writer.** `SetConfig` writes the file with `toml_edit` (format-preserving — the file is hand-written and hand-commented, and a settings tweak that ate the comments would be a worse bug than the one it fixed) via a temp file and a rename. The watcher then compares the text it reads against the text already applied and skips when identical, which makes the daemon's own writes and an editor's no-op save free in one rule, with no bookkeeping about who wrote last.

**Validation is asymmetric, deliberately:**

- **Unknown keys are warnings.** The key is dropped, reported in `ConfigState.warnings`, and the rest of the file still applies. A config written for a newer teiryod must not stop an older one from polling.
- **Wrong-shaped values reject the whole file.** A negative interval, a non-boolean `enabled`, a TOML syntax error, or an interval below `MIN_POLL_INTERVAL_SECS` (10 s — below that a typo hammers a provider's usage endpoint hard enough to get the account rate limited, costing the user the very data teiryo exists to collect) means nothing from the file is applied. The previously applied config keeps running and `ConfigState.error` says why. Partial application would leave the user unable to reason about which half took effect.

**A bad config is never fatal.** Config is loaded inside `run()`, after the socket bind — a daemon that refuses to start over a typo leaves the user with no client to see the typo in. Startup on a rejected file uses defaults and reports the error.

## Logging & errors

- `tracing` → log file, always without ANSI escapes. A second `tracing` layer writes to stderr only when stderr is a terminal (`mise run daemon`). The TUI redirects a spawned daemon's stderr into the same log file, so a stderr layer there would write every line twice, once in color; that redirect is still what catches a panic or anything printed before `tracing` starts.
- `thiserror` for errors crossing the IPC boundary (`Response::Err(ErrorKind, String)`); `anyhow` for internal daemon glue.
- Credentials use `secrecy::SecretString`: no `Debug`/`Display` leakage, zeroized on drop. Never derive or hand-write `Debug`/`Display` on anything holding a credential.
